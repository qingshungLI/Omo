# Recallo 2.0 截图溯源与上下文化可行性调研

日期：2026-07-20  
状态：第一轮桌面研究；尚需真实样本验证

## 1. 研究问题

用户只做一个低成本动作：捕获当前屏幕，并把它发送给 Recallo。

系统是否能自动完成：

```text
截图
→ 理解截图中的高价值片段
→ 找到对应的原始文章、视频或帖子
→ 抓取原始内容
→ 定位截图在原文中的位置
→ 补充恰当的上下文
```

本轮研究的重点不是讨论溯源失败后的 UI，而是先确认这条链路在不同输入条件下能做到什么程度。

## 2. 结论摘要

这条链路可以成立，但不能被实现成单一的“截图反向搜索”。更可靠的产品定义应该是：

> 用系统上下文、截图文本、平台线索和视觉匹配共同寻找来源，再用现有的链接抓取能力完成上下文化。

系统需要区分三种不同强度的输入：

1. **截图 + 原始 URL / 页面对象**：来源确定，链路成功率最高；
2. **截图 + 可识别的平台、作者、标题或独特文本**：可以搜索候选并验证，成功率取决于公开索引和内容可访问性；
3. **只有截图，且没有独特文本或来源线索**：只能做视觉检索或语义猜测，无法稳定保证找到原文。

因此，“截图”应继续作为统一的用户心智，但系统内部不应假设输入永远只有图片字节。能够随截图一起获得的 URL、页面对象、App 来源和时间等信息，都应成为溯源证据。

## 3. 现有 Recallo 已经具备什么

现有 1.0 后端已经具备完整的“已知 URL 之后”的处理链：

### 3.1 文章

`backend/src/sources/extractSourceContent.js` 已经支持：

- 普通网页 URL 抓取；
- HTML 正文、标题和站点信息提取；
- 微信公众号静态 HTML 抽取；
- 静态抓取失败后使用 Playwright 加载公众号页面；
- 超时、非 HTML、正文过短等失败分类。

### 3.2 视频

`backend/src/media/extractVideoLearningSource.js` 已经支持：

- 抖音、小红书 URL 通过 TikHub 解析元数据和媒体地址；
- YouTube、Bilibili 和部分公开视频通过 yt-dlp 取源；
- 优先使用平台字幕，没有字幕时通过 ffmpeg 抽音频并做 ASR；
- 抽取关键帧并调用视觉理解 provider；
- 合并标题、作者、文案、字幕、时间戳和视觉片段，形成 `LearningSource`；
- 保存来源引用、内容依据和提取诊断。

### 3.3 关键缺口

现有所有抓取器的共同前提都是：**输入已经包含一个 URL。**

TikHub 负责把抖音或小红书分享链接解析成内容，不负责从任意截图识别视频。yt-dlp 同样需要 URL。文章提取器也只能在 URL 已知后抓取正文。

因此 2.0 不需要重写现有取源和内容理解框架，但需要在它前面新增一个独立能力：

> `Screenshot Source Resolver`：从截图及系统上下文生成候选 URL，并用证据验证最可能的原始来源。

## 4. iOS 入口能提供哪些证据

### 4.1 普通截图后使用 Share Extension

用户截图后打开截图预览，点击分享并选择 Recallo，这是最容易理解和实现的主入口。

Share Extension 可以接收图片附件。但当用户分享的是一张截图时，不能假设系统还会自动附带截图之前所在 App 的 URL。大多数情况下，Extension 能确定收到了一张图片，却不知道图片来自哪个页面。

因此这条入口的典型输入是：

```text
截图图片
+ 截图文件自身信息
+ 有限的分享上下文
```

它仍然需要真正的反向溯源。

### 4.2 Shortcut + “接收屏幕上的内容”

iOS Shortcuts 支持 `Receive What's On Screen`。当 Shortcut 通过 Siri、轻点背面或其他方式运行时，受支持的 App 可以把当前屏幕上的结构化内容传入 Shortcut。Apple 列举的例子包括 Safari、Maps 和 Photos；输入类型可以是 URL、Safari 页面、图片、文本等。

这给 Recallo 一条更强的增强路径：

```text
轻点背面 / Action Button
→ 运行 Recallo Shortcut
→ 获取当前屏幕对象或 URL（受支持时）
→ 同时截取当前屏幕
→ 调用 Recallo App Intent
→ 提交截图 + URL / 页面对象
```

如果当前 App 暴露 URL 或页面对象，系统不再需要猜来源。截图负责表达“用户选中了这一帧”，URL 负责可靠取源。

限制是：

- 用户需要主动安装或配置 Shortcut；
- 轻点背面需要在系统设置中绑定；
- 不是所有第三方 App 都会提供有用的屏幕对象；
- 抖音、小红书等 App 是否会传出公开 URL，需要逐 App、逐系统版本实测，不能预先承诺。

因此它适合作为高价值增强入口，而 Share Extension 仍应作为通用保底入口。

## 5. 截图反向溯源的候选发现链

当没有 URL 时，建议同时运行多类线索提取，而不是让一个多模态模型直接猜来源。

### 5.1 OCR 与版面分析

从截图中提取：

- 正文句子；
- 标题；
- 作者或账号；
- 平台名称和 UI 特征；
- 视频字幕；
- 用户名、水印、话题标签；
- 发布时间、集数、页码等辅助线索。

OCR 应保存文字的屏幕坐标，区分内容正文与平台导航、评论、按钮等界面文字。

### 5.2 平台识别

通过状态栏以外的界面结构、图标、按钮位置、水印和文字模式判断内容可能来自：

- 微信公众号；
- 小红书；
- 抖音；
- Bilibili；
- YouTube；
- Safari 或其他网页；
- 电子书、PDF、聊天或未知来源。

平台识别的作用不是直接证明来源，而是约束后续检索范围。

### 5.3 文本检索

从 OCR 结果选择一到三段具有区分度的短语进行检索：

- 优先完整、独特、连续的 12–40 字文本；
- 同时加入作者、账号、主题或平台域名；
- 对字幕换行、OCR 错字和中英文标点做容错；
- 对候选页面进行全文抓取，而不只相信搜索摘要。

普通网页、公众号和文字型帖子最适合这条路径。公开网页中出现的独特句子通常比视觉相似更有识别力。

可用的正式搜索 API 需要重新选择。Google Custom Search JSON API 已不接受新客户，并计划于 2027-01-01 停止现有客户使用；Bing Search APIs 已于 2025-08-11 退役。当前可评估 Brave Search API 或其他具备合法生产授权的搜索服务。

### 5.4 平台内候选搜索

如果截图识别出平台、账号或标题，可优先调用平台搜索能力生成候选：

- YouTube Data API 可以按关键词检索公开视频；
- 对抖音、小红书，可用公开搜索结果或合规的第三方 provider 生成候选 URL；
- TikHub 在这一步的潜在作用是平台搜索或候选详情验证，而不是直接接受图片完成溯源；具体端点、授权边界和稳定性仍需专项验证。

平台内搜索通常比全网搜索更适合短视频，因为视频字幕未必被通用搜索引擎索引。

### 5.5 Web 图片匹配

Google Cloud Vision Web Detection 可以返回：

- 完全匹配图片；
- 部分匹配图片；
- 包含匹配图片的网页；
- 视觉相似图片和 Web 实体。

这对以下截图可能有效：

- 文章中的配图或图表；
- 被多个网页转载的图片；
- 视频封面或具有辨识度的关键帧；
- 截图裁剪后仍保留原图主体的内容。

但它不能作为唯一主链：平台 UI、字幕和按钮会改变图像；任意视频帧可能从未被公开索引；纯文字截图的视觉匹配价值也通常低于 OCR 文本搜索。

## 6. 候选来源不能由 LLM 直接拍板

候选发现之后必须有独立的验证阶段。

建议为每个候选 URL 抓取正文、字幕或视频帧，再计算多种证据：

- OCR 文本是否在候选正文或 transcript 中出现；
- 作者、账号、标题和平台是否一致；
- 截图中的图片是否与候选页面图片或视频帧相似；
- 候选时间点附近的字幕和视觉内容是否同时吻合；
- 来源是否为原创、转载或聚合页面；
- 候选是否可以被现有 Recallo 抓取链稳定处理。

LLM 可以帮助生成搜索查询、纠正 OCR 和解释证据，但不能在没有可验证匹配的情况下输出一个确定 URL。

内部建议使用证据状态，而不只存一个布尔值：

```text
exact_context       系统入口直接提供 URL / 页面对象
verified_match      多项独立证据验证同一候选
probable_match      有强匹配，但仍存在替代候选
unresolved          没有足够证据定位来源
conflicting         多个候选证据冲突
```

## 7. 不同内容类型的初步可行性

| 截图类型 | 可行性判断 | 主要依据 | 主要断点 |
| --- | --- | --- | --- |
| Safari 中的公开文章，Shortcut 同时取得 URL | 高 | URL 可直接进入现有文章抓取器 | 动态页面、登录墙、反爬 |
| 公众号文章，截图含独特句子或账号 | 中高 | OCR 精确短语 + 账号搜索，再用现有公众号抓取验证 | 搜索引擎收录不完整、页面访问限制 |
| 普通网页文章，仅有文字截图 | 中高 | 独特句子通常可全网检索 | 改写内容、OCR 错误、付费墙 |
| YouTube/Bilibili，截图含标题或字幕 | 中 | 平台搜索生成候选，再用 yt-dlp/字幕验证 | 字幕未公开、同文案搬运 |
| 抖音/小红书，截图含账号、水印、标题或字幕 | 中 | 平台线索 + 候选搜索 + TikHub 详情/媒体验证 | 缺少稳定公开搜索接口、内容下架或私密 |
| 视频中纯画面，无文字、账号或平台线索 | 低 | 只能依赖 Web 图片匹配或视觉近似 | 该帧可能从未被索引，误匹配风险高 |
| 私密内容、聊天、课程 App、付费内容 | 低或不可溯源 | 截图本身仍可理解 | 原文不可公开访问，也不应绕过权限 |

以上是能力分级，不是已经测出的成功率。真正的产品决策必须基于真实截图样本集测量。

## 8. 推荐的端到端逻辑链

```text
Capture Gateway
  接收 screenshot
  可选接收 URL / Safari page / shared item / source app hint

→ Screenshot Understanding
  OCR + bounding boxes
  平台/UI 识别
  作者、账号、标题、字幕、视觉主体提取

→ Source Resolution
  1. 直接上下文 URL
  2. OCR 独特短语全网搜索
  3. 平台内候选搜索
  4. Web 图片与关键帧匹配

→ Candidate Verification
  抓取候选正文/视频
  文本、作者、平台、图片、帧、时间戳多证据匹配
  输出来源置信状态

→ Existing Recallo Extraction
  文章抓取
  TikHub / yt-dlp 取源
  字幕 / ASR / 关键帧理解
  形成 LearningSource

→ Context Localization
  在全文或 transcript 中定位截图片段
  提取片段前后的最小必要上下文
  保存来源证据和时间点

→ Future Recall Transformation
  尚未定义：回忆、提问、解释、关联或其他体验
```

## 9. MVP 建议

不要一开始承诺“任何截图都能自动找到原文”。建议先验证两条互补入口：

### 通用入口

```text
截图 → Share Extension → 图片溯源
```

验证真实世界中无 URL 截图的来源恢复上限。

### 增强入口

```text
Back Tap / Action Button → Shortcut → 截图 + 屏幕对象 → App Intent
```

在 Safari 等受支持场景中获得接近确定性的来源。

两者最终进入同一个后端 `Capture Gateway`，不形成两套产品数据模型。

## 10. 后续开发阶段的真实样本验证

以下验证不属于当前产品大方向脑暴的下一步。它应在进入开发、技术方案细化或相关交互设计时再启动。

在决定失败体验之前，建议建立 100 张左右的截图溯源测试集，至少覆盖：

- 20 张公众号和普通中文文章；
- 20 张小红书图文或视频；
- 20 张抖音视频；
- 10 张 YouTube / Bilibili；
- 10 张英文网页；
- 10 张只有画面、几乎没有文字的视频帧；
- 10 张私密、聊天、付费或本来就不可能公开溯源的边界样本。

每张样本应保存人工标注的真实来源，并测量：

- 是否得到正确 URL；
- 正确 URL 是否排在候选首位；
- 是否错误地给出高置信来源；
- 是否定位到正确原文段落或视频时间点；
- 端到端耗时；
- 搜索、视觉、取源和模型成本；
- 各平台、各入口和各线索类型的成功率。

最重要的指标不是总体“找到了多少”，而是：

> 在系统声称找到来源时，它有多大概率真的正确。

## 11. 当前判断

截图溯源不是一个可以完全依靠大模型解决的问题，而是一个多阶段信息检索与证据验证问题。

基于现有 Recallo 能力，完整链路中最昂贵的文章/视频抓取、ASR 和视觉理解部分已经存在。真正需要验证的新核心是：

1. iOS 捕获时能携带多少屏幕上下文；
2. OCR 与平台识别能否稳定产生高区分度线索；
3. 搜索服务对中文内容和短视频平台的覆盖；
4. 多证据验证能否把错误归因率压到可接受水平。

在真实样本结果出来之前，不应决定“无法溯源时是否照常回顾”，也不应把“自动找到原文”写成无条件产品承诺。
