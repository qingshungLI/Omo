# Omo 临时 Plans 维护规范

`plans/README.md` 是永久规范；同目录下其他 Markdown 文件是主题分支内的临时施工状态。计划服务于开工审查、多人分工、阶段推进、恢复和验收，不作为完成后的稳定文档。

稳定事实进入 `docs/`；计划过程由 Git 提交历史保存。

## 什么时候需要计划

简单拼写、单点文案、范围明确且一次验证即可完成的局部改动可以不建计划。满足任一条件时必须建计划：

- 跨 iOS、后端、数据库、部署或多个稳定文档。
- 需要分阶段施工或多种验证。
- 预计包含多笔实现提交。
- 改变 API、Schema、持久化、调度、来源证据或兼容行为。
- 涉及隐私、权限、素材授权、付费、发布、迁移或其他高风险决定。
- 需要多个 Agent 并行。
- 用户明确要求先写计划。

## 文件、身份与分支

- 从最新集成基线创建职责单一的主题分支。
- 计划文件使用 `plans/<branch-slug>.md`；把分支名中的 `/` 替换为 `-`。
- 示例：`fix/capture-group-retry` → `plans/fix-capture-group-retry.md`。
- 不使用全局递增编号，也不依赖 Agent 自己生成的随机 ID。
- 计划路径是当前 checkout 内的唯一身份；每个计划必须在 [[PLANS]] 中登记。
- 一个分支原则上只有一个主计划。可独立评审、验证或回滚的范围应拆分分支。

## 幂等规则

### 创建

1. 由当前分支名确定 slug 和计划路径。
2. 创建前检查该路径是否存在。
3. 不存在：从模板创建并在 [[PLANS]] 登记。
4. 已存在且分支一致：恢复原计划，保留决定和证据，不重新初始化。
5. 已存在但负责人或分支不一致：停止写入，先完成显式移交或修正 checkout。

任何 Agent 都不得覆盖已有计划来“重新开始”，也不得为同一分支再建第二个近似名称的计划。

### 登记

- [[PLANS]] 以计划路径为唯一键。
- 重复登记时更新已有行的负责人、状态、进度和下一步。
- 如果同一路径出现多行，先去重再继续。
- `PLANS.md` 只反映当前 checkout，不用于推断其他分支的实时状态。

### 完成与退役

- 只有验收和验证证据完整时才能进入 `completed`。
- 先提交 `completed` 状态与最终证据，再删除计划和索引项。
- 如果计划文件和索引项都已不存在，重复退役是 no-op；不要重建文件只为再次删除。
- 如果只删除了一处，修复剩余项并在提交说明中记录原因。

## 状态

- `proposed`：候选方案，尚未获准施工。
- `approved`：范围、验收、依赖和分工已确认。
- `in_progress`：当前分支正在施工。
- `blocked`：存在明确阻塞，并记录解除条件。
- `completed`：验收与验证已完成，等待退役。
- `cancelled`：明确停止，等待记录原因后退役。

不同主题分支可以同时存在 `in_progress`，不要求全仓库唯一。

状态只能按有证据的实际情况更新；“Agent 正在运行”不等于 `in_progress`，“代码已经写完”不等于 `completed`。

## 推进模式

- `auto`：仓库内、可回滚、属于已确认目标、无外部副作用；范围、验收、验证和依赖明确后可连续推进。
- `manual`：涉及产品方向、公开发布、外部消息、权限、付费资源、生产数据、破坏性迁移、隐私边界、密钥或其他需要新授权的工作。

推进模式不创造授权。`manual` 计划只有在用户已经明确批准相应动作时才能进入 `in_progress`。

## 多 Agent 字段

需要并行工作时，计划必须额外写清：

- 主负责人和最终整合者；
- 每个 Agent 的分支/worktree；
- 每个 Agent 的可写路径；
- 禁止修改的路径；
- 共享 Schema、接口和 Fixture；
- 高冲突文件的唯一写者；
- 每个 Agent 的验证和停止条件；
- 依赖关系与合并顺序。

子任务完成后由主负责人把结果、证据和未完成项收回主计划。不要把聊天记录当作唯一交接载体。

## 计划模板

```markdown
# 计划标题

- 状态：`proposed`
- 优先级：P1
- 创建：YYYY-MM-DD
- 更新：YYYY-MM-DD
- 负责人：Human / Agent name
- 整合者：Human / Agent name
- 分支：`type/short-name`
- Worktree：`<absolute-or-team-agreed-path>`
- 依赖：无
- 推进模式：`auto`
- 可写路径：`path/a`、`path/b`
- 禁止路径：`path/c`
- 高冲突文件唯一写者：无

## 动机与证据

为什么值得做，当前问题如何复现，已有证据是什么。

## 范围

- 本计划会改变什么。

## 非目标

- 明确不做什么。

## 合同冻结

- 输入：
- 输出：
- Schema / API：
- 兼容要求：
- 失败语义：

## 分工

| 子任务 | 负责人 | 分支 / Worktree | 可写路径 | 验证 | 停止条件 |
|---|---|---|---|---|---|
| 示例 | Agent A | `agent/example-a` | `backend/src/example/` | `node --test ...` | 合同需要变化 |

## 任务

- [ ] 可验证任务一。
- [ ] 可验证任务二。

## 验收标准

- 用户或工程层面的完成条件。

## 验证

- 命令、测试、设备、视口或人工检查。
- 真实环境验证与 Fixture 验证分开记录。

## 原则检验

- 证据边界：
- UI / 美学：
- 可访问性：
- 隐私与素材：

## 决定记录

- YYYY-MM-DD：创建计划。

## 阻塞与恢复

- 当前阻塞：无。
- 解除条件：
- 下一位 Agent 从哪里继续：

## 相关文档

- [[docs/index]]
```

## 提交与生命周期

### 1. 开工提交

任何实现前：

1. 写完整计划并在 [[PLANS]] 登记。
2. 运行 `npm --prefix backend run docs:check`。
3. 单独提交计划与索引，提交信息使用 `plan: <slug>`。

第一笔提交不得混入实现，确保评审者能看到原始范围、非目标、合同和验收标准。

### 2. 施工推进

- 按任务列表推进；完成代表已有可检查产物，不代表“尝试过”。
- 每个可验证阶段同步更新勾选项、决定记录、验证和下一步。
- 范围增加时先更新计划；可独立交付的大范围另开分支和计划。
- 稳定事实在同一阶段进入 `docs/`，不得留在临时计划里充当长期文档。
- Agent 移交时更新“阻塞与恢复”，使下一位 Agent 不依赖聊天上下文即可继续。

### 3. 完成或取消

- 完成：所有验收满足后，把状态改为 `completed`，记录最终命令、结果、真实环境证据与必要人工验证，提交 `plan: complete <slug>`。
- 取消：把状态改为 `cancelled`，记录原因、已产生的安全产物和未落地范围，提交 `plan: cancel <slug>`。

### 4. PR 前退役

完成或取消提交之后：

1. 删除任务计划。
2. 从 [[PLANS]] 移除对应活动项。
3. 确认稳定事实已进入 `docs/`，未完成范围已有去向。
4. 运行 `npm --prefix backend run docs:check` 与 `git diff --check`。
5. 单独提交 `plan: retire <slug>`。

最终 PR 的文件差异不应新增已经完成的临时计划，但提交列表应保留计划的创建、完成/取消和退役记录。

## 合并规则

依赖临时计划历史的 PR 禁止 squash merge。默认使用 merge commit，使原始提交 SHA 和计划生命周期成为 `main` 的可达历史。

PR 正文应记录：

- 临时计划路径。
- `plan: <slug>` 开工提交。
- `plan: complete <slug>` 或 `plan: cancel <slug>` 提交。
- `plan: retire <slug>` 提交。
- 最终验证证据。
- 稳定文档位置。
- 尚未验证或需要人工授权的事项。

## 冲突与移交

- 同名计划冲突：以分支归属和 Git 历史为证据，不按文件修改时间或 Agent 自报覆盖。
- 负责人变更：在计划中追加移交记录，更新 [[PLANS]]，保留原负责人和原因。
- 合同变化：所有依赖方暂停施工，由主负责人更新合同冻结区并通知各分支。
- 高冲突文件：只由计划指定的唯一写者整合；其他 Agent 提供补丁、测试或明确的修改说明。
- 主线变化：在主题分支同步并解决冲突，不删除或静默重写队友成果。

## 从 Git 历史取回计划

计划退役并合入后可以使用：

```bash
git log main -- plans/fix-capture-group-retry.md
git log --diff-filter=D --summary main -- plans/fix-capture-group-retry.md
git show <plan-commit>:plans/fix-capture-group-retry.md
git show <complete-commit>:plans/fix-capture-group-retry.md
```

如果只知道 PR，先查看提交列表，再定位 `plan:` 提交。计划长期可追溯依赖非 squash 合并。
